## Naming Conventions
1. **Packages**: Named based on specific functional modules, lowercase
    - e.g., `exercise`, `discuss`
2. **Variables**: Use lower camel case format
3. **Exception Classes**: End with `Exception`
4. **Test Classes**: Start with the class name being tested, end with `Test`
5. **Enum Classes**: Enum member names should be all uppercase with words separated by underscores; constructor methods should be `private`
6. **Naming**: Use complete words instead of abbreviations; prohibit using acronym-based naming to achieve self-documentation
7. **Constants**: Use all uppercase letters with words separated by underscores
    - Global constants: `public static final`
    - Private constants: `private static final`

## Code Formatting
1. **Blank Line Separation**: Use blank lines after interface method definitions, between property definitions and methods, and between different logics, semantics, and businesses
2. **Code Generation**: Base code for various library tables and layers should be automatically generated through the `CodeGenerator` class
    - Currently, code generated by `CodeGenerator` differs from project requirements; template files need modification
3. **Class Length**: Single class should not exceed 500 lines
4. **Method Length**: Single method should not exceed 50 lines
5. **Method Parameters**: Should not exceed 5 parameters. For long parameter lists, wrap them into classes, pass implicitly, or place in collections
    - For many parameters, handling compatibility between old and new interfaces is troublesome; recommend using object encapsulation
6. **Magic Values**: Avoid magic values; define them as constants or enums first
7. **Single-line Comments**: Place comments on separate lines, not on the same line after code
8. **Code Formatting**: Use IDE tools for automatic formatting: `pmd-eclipse-code-formatter.xml` / `java-eclipse-code-templates.xml`
9. **IDEA Setup**: Install "Adapter for EclipseCodeFormatter" plugin to adapt to the above `pmd-eclipse-code-formatter.xml`
10. **Mapper.xml**: In IDEA, set Sql Dialects to MySQL for unified formatting

## Code Logic
1. **Primary/Secondary Logic**: Separate different levels of logic; don't write different hierarchical logic in one large method. Extract secondary logic into independent methods to make main code logic clearer
2. **Common/Specific Logic**: Separate common and specific logic; extract common logic (e.g., parameter validation, permission checks) into shared methods for reuse and maintenance
3. **Control Statements**: Do not allow assignment operations in conditional expressions, nor complex logical combinations in judgment expressions (e.g., multiple `==`, `!=`, `&&`, `||`). Assign complex logical operations to boolean variables with business meaning
4. **Nested Levels**: Do not exceed 3 levels. Use guard clauses, strategy pattern, state pattern, etc. Use `return` statements for early returns to reduce judgment levels
5. **Negation Logic**: Use negation logic sparingly

## Data Collections
1. **String Arrays**: Use `String[] objA` format when defining String array objects
2. **Array to List**: Use `Arrays.asList` for conversion. Avoid setting values in the resulting List as this directly changes the original array values. Also, cannot perform operations that modify element count
    - The converted List is an immutable list; cannot add or delete elements
3. **Collection to Array**: When converting collections to arrays, must use the parameterized `toArray(T[] array)` method
    - e.g., `listObj.toArray(T[] array)`, need to pass an array object type that exactly matches the collection's element type, with length 0
4. **Generics**: Distinguish between the following different definitions:
   ```
   <?> Any type
   <T> Can only place one type
   <? extends T> Can assign to any T or T subclass collections, upper bound is T. Retrieved types have generic restrictions, upward cast to T. Put functionality limited, suitable for frequent reading
   <? super T> Can assign to any T or T parent class collections, lower bound is T. Get functionality limited, suitable for frequent insertion
   ```
5. **Collections Class**: Note that some methods return immutable lists
    - e.g., `emptyList()` / `singletonList()` return immutable lists; cannot add or delete elements
6. **foreach Loops**: Do not perform element `remove` / `add` operations in foreach loops
    - Use `Iterator` method for remove operations. If concurrent operations, need to lock the iterator object
7. **Collection Initialization**: Specify initial collection size when initializing
8. **Ternary Operator**: When using ternary operator (`condition ? expression1 : expression2`), note that when aligning types of expression1 and expression2, may throw NPE exceptions due to automatic unboxing

## Exception Usage
1. Clarify 3 questions about exception usage:
    - Where did the exception occur? Who handles the exception? How to handle the exception?
2. **Exception Classification**:
    - **Error**: System encountered uncontrollable error, only manual intervention possible, e.g., `StackOverflowError`, `OutOfMemoryError`
    - **Checked Exception**: Needs explicit handling in code, otherwise compilation error, e.g., `SQLException`, `ClassNotFoundException`
    - **Unchecked Exception**: Normally inherits from `RuntimeException`, is runtime exception, doesn't require explicit catching and handling

### Checked Exception Subclassification (2 types)
1. **Helpless, Attention Required**: Program cannot handle this exception
    - e.g., `SQLException` caused by field length exceeding limits. General approach: completely preserve exception scene for manual resolution
2. **Capable, Calm Handling**:
    - e.g., `UnauthorizedException`, `ShiroException`, `RuntimeException` occurring. Program automatically redirects to login/registration page

### Unchecked Exception Subclassification (3 types)
1. **Predictable Exception**: Should not be generated or thrown, should handle with boundary checks, null pointer judgments, etc.
    - Common examples: `IndexOutOfBoundsException`, `NullPointerException`
2. **Exception Requiring Catching**: Client must explicitly handle this exception, can handle through retry
    - e.g., `TimeoutException` when using Dubbo framework for RPC calls
3. **Transparent Exception**: Mainly generated by framework or system and will handle itself, program doesn't need to care
    - Spring's unified exception handling `GlobalExceptionHandler` belongs to this category
    - e.g., `PTPException`, `ValidationException`, `LoginException`, `BindException`, `LimitAccessException`, `UnauthorizedException`, `TokenTimeoutException`

### Exception Classification Example: Travel Scenario
1. **Earthquake**: Error
2. **Traffic Jam**: Checked exception, capable type, need to catch exception, can depart early or change flight tickets
3. **Flight Delay**: Checked exception, helpless type, can only continuously monitor flight status
4. **Forgot Passport**: Unchecked, predictable exception, can avoid by checking passport before departure
5. **Car Breakdown**: Unchecked exception, although hard to predict, must handle, need explicit catching, e.g., solve by changing transportation
6. **Ticket Machine Malfunction**: Checked exception, transparent exception, let station handle

### Exception Throwing and Catching
1. Use error codes for external open interfaces
2. For company internal cross-application remote service calls, prioritize using `Result` object to encapsulate error codes, error descriptions, etc.
3. For internal application, directly recommend throwing exception objects

### Exception Handling Specifications
1. Don't use exception catching for process control or conditional control
    - Exception design初衷 is to solve various unexpected situations during program running, and exception handling efficiency is much lower than conditional judgment
2. Catch exceptions to handle them, don't catch and then discard without doing anything
    - If don't want to handle it, throw the exception to its caller. The outermost business user must handle the exception, converting it into user-understandable content
3. In transaction scenarios, when throwing exception is caught, if rollback is needed, must pay attention to manual transaction rollback
    - MyBatis Service layer `rollbackFor = { Exception.class, Error.class }` definition already considers transaction rollback
4. Don't use `return` in `finally` block
    - `finally` is normally used for forced closure under abnormal resource states, not for function returns
5. When defining exceptions, distinguish between unchecked/checked exceptions
    - Recommend using industry-defined custom exceptions, e.g., `DAOException` / `ServiceException`

### Common Exceptions
1. **DAOException**
    - Inherits from `RuntimeException`, is unchecked exception. Various exceptions when connecting to database like network connection failure, database lock timeout, insert data failure, etc., can be categorized upward as `DAOException`
2. **ServiceException**
    - Inherits from `RuntimeException`, is unchecked exception. Common Exception for Service layer, when thrown from Spring-managed transaction functions will trigger transaction rollback

## Logging

### Three Reasons for System Logging
1. **Record Operation Trail**: Record operation behaviors and trail data, can analyze user preferences through data, help optimize business logic, provide personalized services for users - `access.log`
2. **Monitor System Running Status**
3. **Trace System Failures**

### Log Levels
1. **DEBUG**: Record information helpful for debugging
2. **INFO**: Record program running scene, although no error occurred here, has guiding significance for troubleshooting other errors
3. **WARN**: Can also record program running scene, but more inclined to indicate potential error possibility here
4. **ERROR**: Indicates current program running encountered error, needs attention. But current error didn't affect system continuation
5. **FATAL**: Indicates current program running encountered serious error event, and will cause application interruption

### Logging Specifications
1. For DEBUG, INFO level logs, use placeholder method to print logs
2. Production environment prohibits DEBUG log output, and selectively outputs INFO logs
3. When using INFO, WARN levels to record business behaviors, must control log output volume to prevent disk space insufficiency
4. Distinguish between WARN and ERROR log levels
    - Both record error-related log levels, don't笼统 output ERROR level logs once errors occur. If output as ERROR, means once appears needs manual intervention
    - ERROR only records system logic errors, exceptions, or violations of important business rules; other errors can be categorized as WARN level
5. When recording logs, consider three questions: Will someone look at this log? What can they do after seeing this log? Can it improve troubleshooting efficiency?
6. Currently, Controller layer uses `@Log` annotation to record API request logs

## Backend Layer Function Definitions
1. **Controller Layer**: Based on interface design, mainly validates request permissions and checks request parameters, while encapsulating Result returns (including error codes and error messages)
2. **Service Layer**: Handles specific business logic
3. **Manager Layer**: General business processing layer, with following characteristics:
    - Layer encapsulating third-party platforms, preprocessing return results and converting exception information, adapting to upper interfaces. e.g., `CacheService`, `ToolsetServerRestService`, `GitSourceManager`
    - Sinking of Service layer general capabilities. e.g., `UserManager`, `RuleSetManager`, `CommitTaskManager`
4. **Mapper Layer**: Encapsulates database operations (CRUD) in Mapper layer

## Layered Domain Model Specifications
- **DO (Data Object)**: This object has one-to-one correspondence with database table structure, transmits data source objects upward through DAO layer. `xxxDO`, where `xxx` is the data table name
- **DTO (Data Transfer Object)**: Data transfer object, object transmitted outward by Service or Manager. `xxxDTO`, where `xxx` is business domain-related name
- **Query**: Data query object, each layer receives query requests from upper layers
- **VO (View Object)**: Display layer object, usually objects defined by interface that need backend to forward to frontend. `xxxVO`, where `xxx` generally relates to requested interface and page

## Controller Layer Code Specifications
1. Return object fields strictly follow interface documentation, don't return too much irrelevant data
    - Can use mapstruct tool to convert DTO
    - Interface request data can be received through Query or VO, can use mapstruct reverse conversion to Dto, passed to service layer
2. For parameters requiring validation, use `@Validated` validation, add validation rules to fields needing validation, can use Group to specify validation scope
    - `@NotBlank(message = "{required}", groups = { ValidateGroup.Add.class, ValidateGroup.Update.class })`
    - `@Size(max = 125, message = "{noMoreThan}")`
3. **Unified Return Object**: `Result`, corresponding code definitions in each module's `ResultCodeEnum`
4. **Avoid Private Methods**: Controller layer should be尽量 lightweight, handle complex business logic through Service layer
5. **Data Filtering/Reorganization**: When filtering or reorganizing returned data in Controller layer, can define dto and dtoMapper in corresponding module for conversion
6. **Controller Splitting**: For objects with many related interfaces, can split Controller functionality
    - e.g., `ExerciseSetController` split into `ExerciseSetController`, `ExerciseSetForExamController`, `ExerciseSetImportExportController`, `ExerciseSetStatisticController`

## Service/DAO Layer Method Naming Specifications
1. Methods getting single object use `get` prefix
2. Methods getting multiple objects use `list` prefix, plural ending, e.g., `listObjects`
3. Methods getting statistical values use `count` prefix
4. Insert methods use `save` prefix
5. Delete methods use `remove` prefix
6. Update methods use `update` prefix
7. Other service methods, like `check`, `validate`, `page`, etc., name corresponding methods based on business logic

## Service Layer Code Specifications
1. Don't perform remote calls or database operations in loops, prioritize batch operations
    - e.g., `IService.saveBatch()`
2. Summarize and use utility classes
    - e.g., `gson` and Hutool `CollectionUtils.isEmpty(list)`
3. **Control Method Complexity**: Can use Extract Method, extract functionally single code segments, form small functions with clear naming, to solve long function problems
    - Define process first by encapsulating common templates
4. **Resource Release**: Release resources in `finally` block
5. **Exception Handling**: Don't use one Exception to catch all possible exceptions
6. **Exception Matching Order**: Prioritize catching specific exceptions

## Mapper/DAO Layer Code Specifications
1. **XXXMapper.xml**: Needs to define an `XXXBaseMap` containing all properties of own library table, excluding associated table (one-to-many, one-to-one) fields
2. **XXXMapper.xml**: Define an `XXXFullMap` that extends `XXXBaseMap`, introducing dependent properties through `association` or `collection` tags
3. **Field Collection Definition**: For field collections needing query, centrally define through `Column_List_XXX_XXXAbbreviation` SQL
4. **Select Queries**: Define select queries, introduce above-defined SQL through `include`, and `LEFT JOIN` associated tables needed for query

## Layer Calling Specifications
1. **Controller Layer**: Can call itself and related Service layer and Manager layer, and common utility classes (e.g., `ApplicationUtil`). Avoid Controller layer directly calling Mapper layer
2. **Service Layer**: Can call its own Mapper, and related Service layer and Manager layer. Avoid Service layer directly calling other objects' Mapper layer
3. **Manager Layer**: General business processing layer, currently used for calling third-party services like git, redis, toolset, etc. Calling rules reference Service layer
4. **Mapper Layer**: Define interfaces, while writing corresponding SQL in Mapper.xml. Pay attention to SQL formatting and reuse, distinguish different select's `resultMap`

## Layered Exception Handling Specifications
1. **Mapper Layer**: Many exception types generated, cannot use fine-grained exceptions for catch
    - Use `catch(Exception e)` method, and `throw new DAOException(e)`. No need to print logs to prevent duplicate log printing when upper level handles exception
2. **Service Layer**: When exceptions occur, must record error logs to disk,尽可能带上 parameters and context information, equivalent to protecting crime scene
3. **Manager Layer**: Use same processing method as Service layer
4. **Web Layer**: Should not continue throwing checked exceptions upward since already at top level. If意识到 this exception will cause page unable to render normally, then should directly jump to friendly error page,尽量加上 friendly error message
    - Open interface layer should process exceptions into error codes and error message methods for return
